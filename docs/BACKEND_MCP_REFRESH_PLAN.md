# MCP 长期账号授权：后端统一实施计划

版本：v2.0 · 日期：2026-11-11 · 状态：MCP 已自建第一版并上线；后端统一方案待评审

关联：[lynse-mcp Issue #2](https://github.com/lynse-ai/lynse-mcp/issues/2)
上一版：[v1.0（2026-10-19）](https://github.com/lynse-ai/lynse-mcp/blob/main/docs/BACKEND_MCP_REFRESH_PLAN.md)——当时 MCP 与后端均无长期授权；v2.0 依据已上线的 MCP 自建实现重写。

交付对象：账号后端负责人、MCP 接入负责人、测试同学。

## 1. 背景与本版目标

第三方客户端通过 Lynse 官网登录、确认授权后，能够在授权有效期内持续调用远程 MCP，不要求用户每日重新登录。

**现状：后端尚无授权/续期接口；MCP 已在官网自建了一套等价能力并上线**（v0.2.0，部署于 `www.lynse.ai` 测试账号体系与 `www.lynse.cn` 正式账号体系）：官网授权页、90 天绝对期 + 30 天空闲滑动的 grant 模型、MCP Token 轮换与重放撤销、授权记录控制台。详见第 2 节。

本版目标由此从「从零建设」改为「**把上游凭据的签发、续期与撤销统一收编进账号后端**」：MCP 自建实现作为迁移基线与语义参照，后端按第 5 节契约交付后，MCP 侧切换数据来源。后端仍无需在本期重做 MCP OAuth、DCR、PKCE 或客户端回调，也不需要延长所有 App/网页登录 Token 的有效期。

账号后端源码仍未在本机核查；第 3 节确认事项继续有效——后端已有等价能力时可直接复用，但须满足本文的绑定、续期和撤销语义，并与 MCP 自建实现对齐。

## 2. 现状：MCP 自建实现（v0.2.0，已上线）

| 环节 | 当前行为（已上线） | 代码依据 |
| --- | --- | --- |
| 官网授权页 | `/platform/oauth`：DCR 开放注册 + S256 PKCE + resource 绑定；登录动作含手机验证码、手机号登录、微信扫码、`token-login`（网页控制台移交登录态）与登出 | `lynse_remote.py` `WebsiteBridge` |
| 长期授权 grant | 90 天绝对期（`LYNSE_MCP_GRANT_DAYS`）+ 30 天空闲滑动（`LYNSE_MCP_REFRESH_IDLE_DAYS`），成功刷新重算空闲期但不越过绝对期；**与浏览器登录会话解耦**，浏览器退出不影响已建立授权 | `lynse_remote.py:419` |
| MCP Token | Access ≤ 900 秒；Refresh 每次轮换，旧 Token 重放撤销整个 grant 家族（`consumed` 记录，依据 RFC 9700 §4.14） | `lynse_remote.py` `exchange_refresh_token` |
| 上游业务 Token | 用户允许授权时从浏览器登录会话取得，加密存于 grant；寿命随官网登录态，**本地截到最长 86400 秒** | `lynse_account.py:57` |
| 上游过期恢复 | 无续期接口；上游过期后 MCP 拒绝调用并提示，用户**回官网重新登录**即把新凭据下发给该账号全部活跃 grant（`_refresh_grant_credentials`） | `lynse_remote.py:568` |
| 授权记录控制台 | 「我的授权」页面经 `/platform/oauth/api/*` 桥接查询/撤销；已撤销与过期记录保留展示至手动删除；契约见 [authorization-records-api.md](authorization-records-api.md) | `lynse_remote.py` `list_authorizations` |
| 撤销 | 客户端 `/revoke` 或控制台撤销均**本地立即生效**：删除 grant 行使整个 Token 家族失效，记录标记 revoked 保留展示 | `lynse_remote.py:_revoke_grant` |
| 客户端注册 | DCR 记录 TTL 365 天（须长于最长 grant，避免活跃授权随注册过期中断） | `lynse_remote.py:125` |

### 当前实现的边界（收编后端的动机）

1. **上游凭据不可续期**：上游业务 Token 随官网登录态、上限 24 小时，后端无续期接口；所谓 90 天免登录实际受上游寿命限制，跨日后需回官网重新登录一次。
2. **撤销与安全事件不联动**：MCP 侧撤销后，已签发的上游 Token 在业务 API 侧仍有效至自然过期；账号封禁、注销、安全退出全设备只作用于业务层，MCP grant 不会同步失效。
3. **授权数据孤岛**：grant 与授权记录存于 MCP 本地加密 SQLite，不属于账号体系；未来第一方客户端（Desktop 等）无法纳入同一授权/撤销体系。
4. **写权限边界依赖 MCP 层**：`lynse:write` 授权的写操作仅靠 MCP 工具级 `confirm` 把关，业务后端无法按授权范围二次校验。

## 3. 后端先确认的事项

请先给出以下结论，再冻结接口；这些问题不要求业务用户提供密钥或 Token。MCP 侧已自建等价语义，答复时可对照 `lynse_remote.py` / `lynse_oauth_store.py` 现有实现核实。

| 确认项 | 需要后端返回的信息 |
| --- | --- |
| 是否已有等价续期机制 | 接口文档、适用登录方式、能否在原 Access Token 过期后刷新、是否支持独立授权和撤销 |
| Token 的实际生命周期 | `expireIn` 的单位、缺失/特殊值含义、绝对过期与活动续期规则、生产/测试差异 |
| 账号安全事件 | 封禁、注销、密码重置、安全退出全部设备时，现有 Token 如何失效 |
| 业务鉴权能力 | 能否识别“由 MCP 授权签发”的 Token，并执行账号权限和授权范围校验 |
| 服务间认证 | 是否已有服务身份、凭据托管、TLS、限流和密钥轮换机制 |
| 用户操作入口 | 现有“我的授权”控制台由 MCP 托管；收编后该页面数据源切换，是否保留 MCP 侧展示层 |

若已有等价接口，交付下面契约的字段映射及差异即可，不必再建一套会话系统。若缺失，再按第 4～6 节实现。

## 4. 目标设计与有效期

调用关系：第三方客户端 → MCP 服务 → Lynse 账号/业务后端。

| 凭据/标识 | 谁持有 | 用途 |
| --- | --- | --- |
| 原账号登录 Token | MCP 的短期浏览器登录会话 | 证明当前登录账号，用于用户确认授权后的首次换取 |
| 上游业务 Token | 后端签发、MCP 服务端加密保存 | 调用 Lynse 业务接口，不返回给第三方客户端 |
| 上游 Refresh Token | 后端签发、MCP 服务端加密保存 | 向账号后端续发上游业务 Token |
| MCP Access/Refresh Token | 第三方客户端 | 只向 MCP 授权服务和 MCP 资源服务使用，不透传给业务后端 |
| `serviceClientId` | MCP 服务端配置 | 账号后端认证的固定服务身份，生产/测试分别配置 |
| `clientId` | MCP DCR 注册记录 | 第三方客户端的动态标识；不是上述固定服务身份，也不证明平台品牌身份 |

按**一次用户确认的 MCP grant 对应一个后端 authorization**，绑定账号主体、服务身份、第三方 `clientId`、MCP 资源地址和授权范围。不同连接不能共用一个上游 Refresh Token，以便单独撤销。现有实现中本地 `grant_id` 即预生成的 `mcpGrantId`，后端 `authorizationId` 需在本地 grant 中建立映射。

有效期对比（目标值 vs 现状）：

| 项目 | 目标值 | 现状（v0.2.0） |
| --- | --- | --- |
| 上游业务 Token | 15 分钟 | 随官网登录态，最长 24 小时 |
| 上游刷新空闲有效期 | 30 天，刷新重算 | 无（上游不可续期） |
| 长期授权绝对有效期 | 90 天，刷新不延长 | 一致（`LYNSE_MCP_GRANT_DAYS`） |
| MCP Access Token | ≤ 15 分钟 | 一致（900 秒） |
| 幂等重试结果保留 | 120 秒 | MCP 内部已串行化刷新并做重放撤销；跨服务幂等键待后端 |
| 撤销传播 | ≤ 60 秒 | MCP 本地立即；业务侧不传播 |

以上数值须由后端与产品确认后配置化。Refresh Token 过期、撤销或账号安全事件仍会要求重新连接。

> 范围说明：本计划面向 MCP 第三方客户端（`lynse:read` / `lynse:read lynse:write`）。第一方客户端（Lynse Desktop 等）未来可作为同一后端授权体系的 OAuth client 纳入统一的授权记录与撤销入口，但 desktop 业务调用需业务 API 按 authorization scope 鉴权后方能真正受控——属后端体系统一后的扩展项，不在本期范围。

## 5. 建议接口契约

### 5.1 通用约定

以下 `/api/auth/mcp/*` 是**服务间 JSON API 建议路径**，不是新增给 Muse 的 OAuth `/token`。可按后端现有路由规范更名。

- 仅允许受信任 MCP 服务通过 TLS 调用，不向浏览器开放跨域访问。
- 默认建议使用 `Authorization: Basic <服务身份与密钥>` 认证；已有 mTLS 等服务认证时可替换。固定服务身份必须在服务端配置，不能由请求正文自行声明。
- 服务认证头仅发给已配置的账号服务专用接口；业务 API 仍只接收上游业务 Token。不得把服务密钥或外部 MCP Token 混入业务调用，也不得跟随重定向向其他地址转发凭据。
- 正式环境仅允许正式 MCP 服务身份和 `https://www.lynse.cn/mcp`；测试环境对应独立身份和 `https://www.lynse.ai/mcp`。凭据、数据库命名空间及校验策略隔离。
- 成功沿用 `{ "code": 200, "data": ... }` 包装；错误必须同时具有正确 HTTP 状态和稳定的机器可读 `error`。
- `expireIn`、`refreshExpireIn` 是秒数；所有 `*ExpiresAt` 是 UTC Unix 秒。ID、账号主体均为字符串。
- 含凭据的响应设置 `Cache-Control: no-store`。网关/APM/应用日志须屏蔽认证头、`accountToken`、`token`、`refreshToken` 及响应正文中的凭据。

### 5.2 创建长期账号授权

`POST /api/auth/mcp/authorizations`

调用时机：用户在官网 `/platform/oauth` 授权页点击“允许”，MCP 已通过服务端保存的 pending 请求及 CSRF 校验后。点击拒绝、仅打开登录页、尚未绑定账号时均不能创建。

请求头增加 `Idempotency-Key: <服务端生成并持久化的随机请求 ID>`。

```json
{
  "accountToken": "<当前有效的原账号登录 Token>",
  "mcpGrantId": "<MCP 预先生成的随机 grant ID>",
  "clientId": "<pending 中已校验的第三方客户端 ID>",
  "mcpResource": "https://www.lynse.cn/mcp",
  "scope": "lynse:read"
}
```

后端必须验证 `accountToken`，由此确定账号主体；不接受请求中的账号 ID 作为身份依据。服务身份、环境、资源地址、scope 均要校验。`scope` 只能是 `lynse:read` 或 `lynse:read lynse:write`，不得超出账号权限或服务端准许范围。MCP 从已保存的授权请求中取这些值，不能照收浏览器临时提交的范围。

成功响应示例，数值仅用于说明格式：

```json
{
  "code": 200,
  "data": {
    "authorizationId": "<后端独立授权 ID>",
    "subject": "<后端验证得到的账号 ID>",
    "clientId": "<第三方客户端 ID>",
    "mcpResource": "https://www.lynse.cn/mcp",
    "scope": "lynse:read",
    "token": "<新的上游短期业务 Token>",
    "expireIn": 900,
    "refreshToken": "<新的上游 Refresh Token>",
    "refreshExpireIn": 2592000,
    "authorizationExpiresAt": 1800144000
  }
}
```

`token` 必须是新授权签发的业务凭据，后端能按 `authorizationId` 撤销。它面向 Lynse 业务 API；`mcpResource` 是该授权的连接绑定信息，不应把上游业务 Token 的 audience 错设为外部 `/mcp`。

创建接口以服务身份、环境及 `mcpGrantId` 保证唯一性。幂等键与请求摘要绑定；同键同请求在保留期内返回同一有效结果，同键不同请求拒绝。不能因网络重试创建多个可续期授权。

### 5.3 刷新上游凭据

`POST /api/auth/mcp/authorizations/refresh`

使用上述服务认证和 `Idempotency-Key`。**不能要求同时提供仍未过期的业务 Token**，否则无法在短期 Token 到期后恢复。此接口替代现状中“回官网重新登录刷新活跃 grant”的人工恢复路径。

```json
{
  "authorizationId": "<后端独立授权 ID>",
  "refreshToken": "<当前有效的上游 Refresh Token>"
}
```

成功返回与创建接口相同的字段，替换 `token` 和 `refreshToken`；主体、客户端、资源和最大授权范围保持绑定，`authorizationExpiresAt` 保持不变。`refreshExpireIn` 不得超过绝对授权剩余时间，业务 Token 有效期也不得越过授权截止时间。刷新不能凭请求扩大权限。

轮换规则：新 Refresh Token 生效与旧 Token 标记已使用必须原子完成。保留已使用 Token 的摘要及所属授权关系，才能识别旧 Token 重放；不能简单删除后只返回“找不到”。MCP 自建实现中的 `consumed` 重放撤销语义（重放即撤销整个家族）与此一致，后端须具备同等能力。

网络与并发规则必须一起交付：

1. MCP 对同一 `authorizationId` 串行刷新；多实例时使用共享锁或等价协调。
2. MCP 在发送请求前持久化幂等键；超时/响应丢失时使用**同一个键与相同请求**重试。
3. 后端在 120 秒建议窗口内返回同一组凭据，不重复轮换；幂等结果中的凭据需加密存储并到期清除。返回缓存结果前仍需检查授权未撤销、未过期。
4. 窗口内同键不同请求返回冲突。已使用 Refresh Token 在非幂等恢复场景再次出现时，撤销该授权的整个 Token 家族，要求用户重新连接。随机无效 Token 不应导致其他授权被撤销。
5. 两个不同幂等键同时使用同一旧 Token，最多一次轮换成功；另一次按重放处理并撤销该授权。MCP 必须靠串行化避免正常并发触发该路径。
6. 超过恢复窗口且 MCP 未能取得新凭据时，要求重新授权，不无限接受旧 Token，也不盲目生成新幂等键继续尝试。

轮换、绑定与重放防护依据见 [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)；本节具体超时和幂等协议属于本项目建议设计。

### 5.4 撤销授权

`POST /api/auth/mcp/authorizations/{authorizationId}/revoke`

仅允许创建该授权的同一服务身份、同一环境执行；请求正文可为空。撤销对应上游 Refresh Token 家族及业务 Token，不能影响该用户的其他 MCP 连接。此接口补齐现状缺口：MCP 侧撤销（客户端 `/revoke` 或控制台操作）目前只能让本地家族失效，已签发上游 Token 在业务 API 侧仍有效至自然过期。

已撤销或不存在的授权返回成功，支持重复调用。其他服务身份不能借此探测或撤销授权；可统一返回幂等成功但不得产生越权副作用。撤销应在后端安全事件及业务鉴权中真正生效，而不是只删除刷新记录。该行为参考 [RFC 7009 的撤销语义](https://www.rfc-editor.org/rfc/rfc7009.html#section-2.1)，接口包装仍按本项目约定。

MCP 收到客户端 `/revoke` 后先立即封禁本地 grant，再可靠地通知后端；后端暂时不可用时进入持久化重试队列。本地授权不因通知失败恢复。

### 5.5 查询授权状态

`GET /api/auth/mcp/authorizations/{authorizationId}/status`

仅同一服务身份可查。有效授权返回 `active: true`、`subject`、`clientId`、`mcpResource`、`scope`、`authorizationExpiresAt`、`refreshExpiresAt`；不返回 Token。不存在、无权访问、已过期或已撤销时统一返回 `{ "code": 200, "data": { "active": false } }`。

MCP 对活跃状态缓存建议不超过 30 秒，并受凭据/授权截止时间限制，用于在下一次请求中识别账号后端发起的撤销；配合后端业务鉴权满足最长 60 秒的传播目标。已有等价的 introspection 或可靠撤销事件机制可替代此接口，但须交付相同的失效上限。

后端不可用时，超出状态缓存有效期的请求应提示暂时不可用，不继续无限信任旧状态，也不把故障误判为永久撤销。

### 5.6 错误与 MCP 处理约定

| HTTP / `error` | 含义 | MCP 后续行为 |
| --- | --- | --- |
| 400 / `invalid_request` | 缺参或格式错误 | 修正调用，不自动重试 |
| 400 / `invalid_grant` | 刷新凭据无效/过期、授权撤销或账号不可继续授权 | 终止该本地授权；提示重新连接；避免返回敏感细分原因 |
| 401 / `invalid_client` | MCP 服务身份认证失败 | 运维配置告警；不要求所有用户重登，不批量删除 grant |
| 403 / `invalid_scope`、`invalid_target` | 创建授权的范围/环境/资源不允许 | 修正配置或授权请求，不降级为共享凭据 |
| 409 / `idempotency_conflict` | 同一幂等键关联不同请求 | 停止该重试并排查状态，不覆盖原结果 |
| 429 / `rate_limited` | 请求过频 | 按 `Retry-After` 和有上限的退避重试 |
| 502/503/504 / `temporarily_unavailable` | 网络、依赖或服务暂时故障 | 不销毁授权；保留同一幂等键恢复；凭据过期后暂停调用 |

业务 API 的 403 权限不足不等于账号过期，不应自动刷新或撤销授权。仅在收到明确的 Token 失效信号时触发兜底刷新。

## 6. 后端内部实现要求

可用现有数据库/缓存实现，无指定语言、框架或存储产品的要求。至少记录：

- 授权：`authorizationId`、固定服务身份、环境、`mcpGrantId`、验证得到的 `subject`、第三方 `clientId`、`mcpResource`、scope、状态、创建时间、绝对截止、空闲截止、撤销时间/原因。
- 凭据：当前 Refresh Token 摘要、代次、已消费 Token 摘要与家族关系；通过事务/比较更新保证原子轮换。高熵随机 Token 不明文落库，摘要算法与密钥按现有安全规范选用。重放识别与撤销语义须与 MCP 自建实现的 `consumed` 机制等价。
- 幂等：认证服务身份、接口、幂等键、请求摘要、加密结果、截止时间；状态与凭据更新须能一致恢复，不能轮换成功却永久丢失结果。
- 撤销：业务 Token 必须能关联授权状态。使用 JWT 时也需查询撤销状态/版本或使用有上限的缓存，不能仅依赖 JWT 自身到期。
- 权限：业务层同时检查账号本身的访问权限与授权 scope；只读授权不能凭上游 Token 调用写接口。需要读操作使用 POST 时，应按业务动作授权，不能仅按 HTTP 方法判断。
- 账号事件：封禁、注销、密码重置/安全退出全部授权时撤销相关 MCP 授权。普通浏览器退出只清当前登录会话；单个连接解绑只撤销对应授权。具体事件与现有安全策略在第 3 节冻结。
- 可观测性：统计创建/刷新成功率、轮换冲突、重放、撤销积压和后端失败；审计仅保留必要的服务身份、授权 ID、脱敏主体、动作及 request ID，不记录凭据或会议内容。

身份、客户端绑定和刷新凭据校验的通用依据见 [RFC 6749 §6](https://www.rfc-editor.org/rfc/rfc6749.html#section-6)。接口授权主体必须来自后端验证，不能来自用户提交的 ID。

## 7. MCP 需要配合的改动

v0.2.0 已完成（后端就绪后直接沿用）：DCR/PKCE/同意页、grant 90+30 天生命周期与浏览器会话解耦、MCP Token 轮换与重放撤销、本地串行化刷新、授权记录控制台与撤销、365 天客户端注册 TTL、`_refresh_grant_credentials` 官网重登恢复路径（作为后端刷新不可用时的兜底保留）。

后端能力可用后仍需完成的适配：

| 位置 | 配合改动 |
| --- | --- |
| `lynse_account.py: AccountBackend` | 增加创建/刷新/撤销/状态适配，区分永久授权失效、服务认证失败与临时故障；校验续期返回的主体和绑定信息 |
| `lynse_remote.py: WebsiteBridge` | 用户允许后改为建立后端授权（替代现状“直接取浏览器会话 Token 存入 grant”）；使用预分配 grant ID 和幂等键；后端成功但本地写入失败时可恢复或补偿撤销 |
| 本地 grant 存储 | 加密保存 `authorizationId`、上游 Access/Refresh Token、各自截止时间、绝对授权截止、刷新版本及待恢复幂等键；旧记录标识为不可续期 |
| `AccountOAuthProvider._issue` 与刷新路径 | 将长期 grant 生命周期与短期上游 Token 生命周期分开（grant 侧已解耦，本项指上游凭据的独立刷新）；仅在有效后端授权内签发/刷新 MCP Token |
| `AccountTools` / 业务调用前 | 上游业务 Token 即将到期时统一刷新并持久化；同一授权串行化；校验账号不变；不能退回本机 CLI/环境中的共享凭据 |
| 业务请求重试 | 读请求可在明确 Token 过期后刷新并重试一次；写请求仅在后端保证执行前拒绝或已有业务幂等保障时自动重试，不能重复执行写操作 |
| MCP `/revoke`、Token 验证 | 本地立即撤销后可靠通知后端；检查后端状态，使封禁/远程撤销在规定时间内生效 |
| 测试与文档 | 补充两层 Token 的独立轮换、故障恢复、跨日连接、到期重连、账号隔离与撤销传播验证 |

本地 grant 的有效截止取“后端绝对授权截止”和“上游刷新空闲截止”中较早者；上游 Access Token 的截止单独保存。成功上游续期后同步更新空闲截止及存储 TTL。现状“上游寿命随官网登录、上限 24 小时”的模型在后端授权建立后退役，官网重登仅刷新浏览器会话本身。

现有 `_issue` 在 SQLite 事务中同步执行。不得直接把网络续期塞进该事务；需拆为“持久化刷新意图 → 事务外调用后端 → 校验版本并原子更新本地凭据”，同时处理期间发生的撤销。若撤销已生效，迟到的刷新结果不得使授权复活。

后端变更与 MCP 变更必须配套发布。仅后端上线，当前 MCP 不具备调用新接口的能力；仅修改 MCP，有效的长期上游凭据仍然缺失。

## 9. 验收标准

下表是双方交付验收。接口自动化可缩短有效期或注入时钟，不需要每次等待真实 90 天。标注「现状已有」的行表示 MCP 自建实现已满足该行为，验收时对照即可。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 手机授权；已配置时的微信授权 | 完成真实身份校验和用户允许后才创建后端授权；拒绝不产生授权（现状已有） |
| 上游短期 Token 过期 | Refresh Token 仍有效时可签发新业务 Token，不依赖旧 Token 仍可用（现状依赖官网重登，收编后自动化） |
| 跨 15 分钟及 24 小时 | 同一 MCP 连接可刷新并继续只读查询，账号不变，无需回官网重登（现状 24 小时需人工重登，为本次核心改进） |
| 原网页登录 Token 过期/浏览器退出 | 已建立的独立 MCP 授权在自身有效期内仍可用，不依赖浏览器保持登录（现状已有） |
| 刷新空闲期/绝对期限到期 | 停止刷新及数据访问，明确要求重新连接；刷新不延长绝对期限（现状已有） |
| 客户端注册期限与授权期限交错 | 注册 TTL 已放宽至 365 天；仍按冻结的续存/重新注册策略处理，不因记录提前清理而无提示中断 |
| 两次轮换/旧 Token 重放 | 新 Token 正常使用；非幂等恢复的旧 Token 重放撤销对应家族，其他连接不受影响（MCP 侧现状已有；后端侧同等验收） |
| 并发刷新 | 相同幂等键只轮换一次；不同键竞争同一旧凭据按约定拒绝/撤销；无两个独立有效后继 |
| 响应丢失/进程重启 | 持久化幂等键能在恢复窗口拿回同一凭据；窗口外安全要求重连，不形成无限旧 Token 宽限 |
| MCP 主动撤销 | 本地立即拒绝调用；后端授权在传播上限内不可用；通知失败可持久化重试（业务侧传播为新增能力） |
| 后端撤销/封禁/安全事件 | 业务调用及 MCP 授权检查在约定上限内拒绝；迟到的刷新响应不能恢复授权 |
| 账号与客户端隔离 | A 账号/连接的凭据不能冒充 B；客户端名或请求中的 ID 不能覆盖真实主体 |
| 环境与服务身份隔离 | 测试凭据不能在正式环境刷新/访问；错误服务身份不能操作授权 |
| 权限边界 | 只读授权调用写接口被后端拒绝；MCP 写操作原有 `confirm=true` 要求继续生效 |
| 后端 5xx/超时/429 | 有上限地恢复，不批量注销授权，不回退到共享 Key；凭据失效后停止调用 |
| 写请求不确定结果 | 不因自动刷新/网络重试重复创建、移动或删除业务数据 |
| 老客户端兼容 | 原 `/api/auth/login` 响应和原 App 登录策略保持兼容；普通客户端不会无意获得长期 MCP 凭据 |
| 真实客户端 | 首选现有可用客户端验证（Codex 已实测只读接入），再验 Muse 的完整 OAuth、工具发现和只读查询；Muse 页面阻塞单独定位，不以模拟客户端替代实测结论 |

上线前至少保留一次测试账号的真实跨 24 小时只读运行记录（现状该场景需人工回官网重登，收编后应免登录通过）；自动化覆盖更长的绝对到期边界。记录仅保留时间、授权状态和结果，不包含 Token、验证码或会议内容。

## 10. 迁移、灰度与回退

1. 后端先部署兼容接口，默认不开启新凭据签发；准备独立的测试/正式服务身份。服务凭据通过受控配置渠道交付，不放进文档或聊天。
2. 测试环境（`www.lynse.ai`）部署配套 MCP 适配，通过接口和故障验收后，再对正式环境（`www.lynse.cn`）的少量连接启用。两套环境已各自运行自建实现，切换按环境独立推进。
3. 已有自建 grant 不会凭空获得后端授权。旧连接维持原截止时间与「官网重登刷新上游」行为，用户下次重新登录并确认授权后进入新机制；不静默扩大旧授权。
4. 「我的授权」控制台由 MCP 托管，收编后保持页面与交互不变，数据源逐条切换为后端授权；已撤销/过期记录的保留展示语义不变。
5. 创建后端授权但本地授权码未成功签发的情况，需要补偿撤销。建议后端未被首次使用的授权在短期内自动清理，具体时限在 B0 冻结。
6. 灰度观察刷新成功率、幂等恢复、重放告警、撤销延迟及错误重登率。临时故障和服务认证配置错误不能被算成“用户授权已过期”。
7. 回退时先停止创建新长期授权，保留新旧记录的识别及撤销通道；未识别新模型的旧 MCP 版本不能直接接管新记录并延长有效期。需回退到不支持新凭据的版本时，先撤销新授权并通知相应用户重新连接，回退连接回落到「官网重登刷新上游」的现行行为。
